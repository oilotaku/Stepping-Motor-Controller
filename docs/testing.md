## `conftest.py` 的 `RECORDING_DIR`／`DATA_DIR` 必須雙邊 patch

**`conftest.py` 的 `make_gui()` 必須同時 `patch.object(main_ai, "RECORDING_DIR", ...)` 與 `patch.object(ds102_ctrl, "RECORDING_DIR", ...)`，只 patch 一邊等於沒防護（2026-08-19 實測踩到）。** `main_ai.py` 是用 `from ds102_ctrl import RECORDING_DIR` 重新引入，這只是另一個獨立綁定同一初始物件的名字；`DS102Controller` 的持久化方法（`save_point`／`set_axis_calib`／`save_recording`／`capture_controller_config` 等）全部定義在 `ds102_ctrl.py`，引用的是該模組**自己的**模組層級綁定，只 patch `main_ai.RECORDING_DIR` 完全攔不到這些方法，會直接寫進專案真正的 `recordings/`。`verify_scan_tab.py`／`verify_meter_panel.py` 之前沒踩到純粹是因為沒呼叫到這些方法，不代表這層防護真的有效——跟本檔記載「測試腳本清空過兩次 teaching points」是同一類風險。已在 `make_gui()` 修好，**任何新增的測試檔案都不需要（也不應該）再自己額外 patch 一次**，但改動 `conftest.py` 本身時要記得這兩邊要同步。**2026-08-21 起 `DATA_DIR` 也比照辦理**（`patch.object` main_ai 與 ds102_ctrl 兩邊，導到 `recording_dir/data`）：新增的 `save_homing_repeat_result()` 寫的是 `DATA_DIR` 而非 `RECORDING_DIR`，理由與上述完全相同——少 patch 一邊，測試就會寫進專案真正的 `data/`。

## 十支測試檔各自的來歷與 `FakeCtrl` 差異

「尋光」／「光功率」分頁／軸機械校正參數／`fiber_scanner.py` 訊號有效性判準／`_wait_axis_stop()` 起步競態／移動控制分頁座標供應鏈／Powell 尋光路徑的假物件回歸測試（合計 379 項 pytest 測試函式，`python -m pytest verify_scan_tab.py verify_meter_panel.py verify_axis_calib.py verify_fiber_scanner_signal.py verify_wait_axis_stop.py verify_ctrl_pos_sync.py verify_blind_scan.py verify_scan_export.py verify_scan_powell.py verify_scan_powell_integration.py -v` 執行，VS Code Testing 面板也認得）。用假的 `ctrl` / `meter` 物件驅動邏輯，不需要真實硬體。`verify_fiber_scanner_signal.py` 是 2026-08-19 從某次 session 的 scratchpad 補進版控並轉成 pytest（原本是獨立可執行腳本），轉換時發現它的 `FakeCtrl` 沒有 `estimate_um()`，因為原腳本寫於 μm 快照功能（見 [docs/axis-calibration.md](docs/axis-calibration.md)）加入之前——`_measure_here()` 現在無條件呼叫這個方法，補上回傳 `None` 的樁即可，不影響任何既有斷言。`verify_wait_axis_stop.py` 是 2026-08-26 修〈孿生競態〉時新增的（29 項），它是唯一一支不建 GUI、直接對 `DS102Controller` 實例逐一 monkeypatch `query_status` 的測試檔，所以沒有用 `conftest.py` 的 `make_gui()`，而是自己 `patch.object` `ds102_ctrl.RECORDING_DIR`／`DATA_DIR`——新增同類測試檔時照抄它的 `ctrl` fixture 即可。`verify_ctrl_pos_sync.py` 是 2026-08-26 修〈移動控制分頁「Position:」的座標供應鏈統一〉時新增的（13 項），用 module-scope 的 `gui` fixture＋autouse 的狀態重置，直接同步呼叫 `_redraw_positions()` 斷言畫面文字。`verify_blind_scan.py` 是 2026-08-26 修〈無光位置尋光無動作〉時新增的（57 項，見 [docs/fiber-scan.md](docs/fiber-scan.md)〈階段零：盲搜粗掃〉），它的 `FakeCtrl` 與 `verify_fiber_scanner_signal.py` 那份**不通用**：盲搜走 `_move_multi_axis()`，該路徑會傳 `start_pos`／`expected_travel` 兩個位移提示，舊的 `wait_axis_stop()` 樁沒有這兩個參數會直接 TypeError；本檔的版本另外支援軟體限位，用來驗證盲搜對超出行程的格點是「跳過並繼續」而不是整批中止。**同日再擴充時新增的 `hard_limits` 與既有的 `limits` 是兩件完全不同的事，別混用**：`limits` 是軟體限位（`ctrl.sw_limits`），送指令前就擋、滑台一步都不會動；`hard_limits` 是實體限位開關，**擋不住任何指令**，軸會真的走到端點停住並讓 `SB1?` 一直回報 `Detect CW/CCW limit`。實機上只有後者存在（`sw_limits` 預設是空的），`TestTravelBounds`／`TestStage1Termination` 要鎖的就是「只有後者存在時不要反覆去撞它」，見 [docs/fiber-scan.md](fiber-scan.md)〈撞限位不再反覆撞〉。同一次改動也讓 `verify_wait_axis_stop.py` 的 `TestScannerBatchMovePassesHints` 那個 duck-typed `FakeScanner` 多了一個 `_targets_reachable`——它刻意借用**真正的**實作而不是回寫死的 True，否則測試會走一條實機不存在的路徑。`verify_scan_export.py` 是 2026-08-26 新增尋光 Excel 報表時建立的（24 項，見 [docs/fiber-scan.md](fiber-scan.md)〈尋光樣本的 Excel 報表〉），它**完全沒有 `FakeCtrl`**——`export_samples_xlsx()` 是純函式、只吃 `Sample` list，這正是當初把它做成模組層級函式而不是 `FiberAlignmentScanner` 方法的原因；只有測 `persist_samples()` 整合的那個 class 需要一個四個屬性的最小 `_Ctrl` 樁。**它刻意真的把 xlsx 寫進 `tmp_path` 再用 `zipfile` 解開內部 XML 讀回驗證，沒有 mock 掉 `xlsxwriter`**：這個功能唯一的價值就是「產生的檔案 Excel 打得開、欄位對得上」，把寫檔那一段換成假物件等於什麼都沒測到。不用 openpyxl 讀回是為了不多一個測試專用相依（venv 沒有）。`verify_scan_powell.py` 是 2026-08-27 新增 Powell 尋光路徑（`fiber_scanner_advanced.run_stage_powell()`）時建立的（8 項），它的 `FakeCtrl` 不建 GUI、直接對著 `run_stage_powell()` 呼叫，涵蓋基本收斂、軸間耦合對照（驗證〈耦合案例對照數據〉那組合成橢圓曲面）、撞限位軟牆懲罰、量測失敗懲罰、使用者中止時滑台回退最佳座標、scipy 缺席時 `RuntimeError`、`objective()` 的座標快取。`verify_scan_powell_integration.py` 是 2026-08-28 把 Powell 接進 `main_ai.py` GUI 時新增的（17 項，見 [docs/fiber-scan.md](fiber-scan.md)〈Powell 尋光路徑接進 GUI〉），它的 `FakeCtrl` 跟 `verify_scan_powell.py` 那份**不通用**——這支要測的是 GUI 分頁與 `fiber_scanner.py._run_primary_algorithm()` 的分流邏輯，不是 `run_stage_powell()` 本身，所以建了 GUI（走 `conftest.py` 的 `make_gui()`），涵蓋端到端跑完 Powell、階段二設定被忽略且有警告 log、無訊號早偵測的兩種情境（第一次吞掉補盲搜／第二次讓例外往外傳）、演算法白名單防禦、下拉切換時 Entry 灰階狀態、scipy 缺席時選單與二次攔截的降級行為。
